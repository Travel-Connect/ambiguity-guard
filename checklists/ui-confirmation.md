# UI 対象特定チェックリスト（ui-confirmation）

「ここ」「この部分」「この画面」の対象を一意に特定するための実用チェックリスト。
SKILL.md「4. UI / スクリーンショット確認」の詳細版。

## 1. 対象特定のチェックリスト

- [ ] 対象の**画面（URL / 画面名 / ルート）**は一意に特定できたか
- [ ] 画面内の**箇所（見出し・ボタン名・ラベル・文言）**は一意に特定できたか
- [ ] 同じ文言・似た見た目の箇所が**複数存在しないか**（一覧と詳細、PC とモバイル等）
- [ ] 対応する**コンポーネント / ファイル / 行番号**まで辿れたか
- [ ] 変更が**他の画面に波及**しないか（共通コンポーネント・共通 CSS か）
- [ ] 状態依存の表示か（ログイン有無・権限・データ件数・エラー時のみ表示 等）
- [ ] レスポンシブ表示で位置・表示有無が変わるか

1 つでも「いいえ / 不明」があり、間違えると出戻りになるなら Gate=B または C。

## 2. スクリーンショットが取れる場合の手順

1. ブラウザ操作ツールを検出順に確認: Claude in Chrome → Chrome DevTools MCP →
   Playwright MCP → Browser MCP → その他。**新規導入はしない。**
   ツールが 1 つも無い場合はサーバーを起動せず「3. スクリーンショットが
   取れない場合の手順」へ進む。
2. ツールがある場合のみ、開発サーバーを起動する
   （起動コマンドは package.json / README で確認）。
3. 対象画面を開き、必要ならログイン・データ投入して該当状態を再現する。
4. スクリーンショットを取得する（機密情報・認証情報が映り込まないことを確認）。
5. 領域を言葉で説明し（「右上の『保存』ボタンの左隣」等）、
   「ここのことですか？」と A/B/C 選択式で確認する。

## 3. スクリーンショットが取れない場合の手順

1. 取れない旨を 1 行で伝える（理由の長文説明はしない）。
2. 下記テンプレートで「画面のどこか」をテキストで特定する。
3. テキストでも絞り込めない場合は、ユーザーにスクリーンショット添付を依頼する
   （Gate=C: Stop and request artifact）。

## 4. テキストで画面箇所を表現するテンプレート

```
[BLOCKING] UI対象の確認です。

私の理解では、修正対象は以下です。

画面: <URLまたは画面名>
候補箇所: <画面上の文言・見出し・ボタン名>
DOM/selector: <分かれば>
コンポーネント: <分かれば>
ファイル: <分かれば>
周辺文脈: <例: 「保存」ボタンの右隣、料金表の3列目、エラー文言の下>

この箇所のことですか？
A. はい、この箇所
B. いいえ、別の箇所
C. 似ているが、対象は <ユーザーに指定してもらう>
```

候補が複数あるときは、候補を番号付きで併記して選んでもらう
（例: 「候補1: 一覧画面の合計欄 / 候補2: 詳細画面の合計欄」）。

## 5. 記録方法（後工程・テストで使うため）

確定した UI 対象は、実装メモまたはテストコメントに以下の形で残す。

| 項目 | 記録例 |
|------|--------|
| URL / ルート | `/admin/plans`（管理画面 > プラン一覧） |
| 画面上の文言 | 見出し「販売プラン」直下のテーブル 3 列目「料金」 |
| DOM セレクタ | `table.plan-list td[data-col="price"]` |
| コンポーネント名 | `PlanListTable`（`src/components/PlanListTable.tsx`） |
| ファイル / 行 | `src/components/PlanListTable.tsx:42` |

- セレクタは動的 id（`#id-38fa2`等）ではなく、文言・data 属性・安定クラス名で書く。
- 「どの認識合わせでこの対象に確定したか」をテスト名かコメントに 1 行残す
  （→ `checklists/test-alignment.md`）。
