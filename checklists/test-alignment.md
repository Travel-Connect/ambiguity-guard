# 認識合わせをテストに落とすチェックリスト（test-alignment）

ユーザーと認識合わせした仕様を、実装後のテスト項目・検証項目に確実に反映するための
手順。SKILL.md「6. 突合・検証・テスト項目」の詳細版。

## 1. 認識合わせした仕様をテスト項目に落とす方法

1. 確定した仕様を 1 項目ずつ列挙する（Gate の質問と回答の対応表を作る）。
2. 各項目に対して「それが破られたら検知できるテスト」を 1 つ以上対応させる。
3. **テスト名またはテストコメントに、どの認識合わせに対応しているかを残す。**
   - 例: `test("合計後に一度だけ四捨五入する（2026-07-07 ユーザー確認: 端数処理はB案）")`
   - 例: `// 認識合わせ: 締め日は月末、当日を含む（ユーザー回答より）`
4. 仕様が確定していないケースは **pending / TODO / skip にしない**。
   テストを書けないなら、それは Gate=B に戻ってユーザーに確認するサイン。

## 2. 突合データをテスト化する方法

- ユーザーが示した期待値・サンプル・既存結果・CSV・画面表示・ログ・DB 結果がある場合、
  **「突合した検証結果と一致すること」**をテスト項目に追加する。
- 期待値はテストコード内に**出所つき**で埋め込む
  （例: `// 期待値 10,235 円: ユーザー提供 CSV billing_2026-06.csv 行 12 より`）。
- CSV・DB との突合は、可能なら固定サンプル（fixture 化した数行）で再現可能にする。
  外部ファイル依存のままにしない。
- 期待値がない場合は、実装前に代表ケース（正常系 1 件以上）の期待値をユーザーに確認する。

## 3. テスト項目に含めるべき例

- 突合した期待値と一致する
- 税込 / 税抜の扱いが一致する
- 端数処理が一致する（明細ごと / 合計後の別も含む）
- 境界日付で一致する（締め日当日・月末・年末年始・うるう年）
- null / 0 / 空入力で壊れない
- UI 対象箇所のみ変わっている（意図しない箇所が変わっていない）
- 既存挙動が維持されている
- 回帰テストが通る

## 4. UI 変更の確認観点

- [ ] 確定した対象箇所（`checklists/ui-confirmation.md` の記録）だけが変わったか
- [ ] 同じコンポーネントを使う**他画面に波及していない**か
- [ ] 画面で確認できる場合は、実装後にブラウザで実際に表示確認したか
- [ ] スクリーンショットを取れる環境なら before / after を取得したか
  （機密が映り込まないこと）

## 5. 回帰テスト観点

- [ ] 変更したファイルに関する既存テストがすべて green か
- [ ] 計算変更の場合、**既存レコード・既存画面の値が変わらない**ことを確認したか
  （変わるのが正なら、その旨をユーザーに確認済みか）
- [ ] lint / typecheck / build が通るか

## 6. 実装完了報告テンプレート

```
実装完了です。

確認して確定した仕様:

* <仕様>

置いた仮定:

* <仮定。なければ「なし」>

変更箇所:

* <ファイル/概要>

追加・更新したテスト:

* <テスト名/観点>
* <突合した期待値があればその内容>

確認結果:

* <コマンド/画面確認/突合結果>

未確認・次に確認すべきこと:

* <なければ「なし」>
```
